# Frontend API contract
All app endpoints are relative to /api. Lists currently return arrays. Auth uses server session cookies (implementation pending). Server must enforce ownership and roles. GET /posts/{id} is read-only; POST /posts/{id}/views requires no body and increments the count on every request. One detail mount is one visit; refresh/reopen counts again. Increment atomically. Do not count editor or likes/comments refresh.
Favorite ordering: last_clicked_at DESC, initialized on favorite creation, updated when a signed-in user opens a favorited work. The backend must enforce user ownership. SQL migration is provided, not applied.
KMAS official guide: https://www.kmas.or.kr/guide/openapi — bookAndWebtoonList, prvKey, pageNo (default 0), viewItemCnt (max 100); guide lists title, isbn, pictrWritrNm, sntncWritrNm, pltfomCdNm, plscmpnIdNm as search fields. Keep approved KMAS key on Spring Boot server, never VITE_ variables. Official guide states 1,000 daily requests. Live response not verified. Filter to webtoon records where supported; do not assume all results are webtoons.
Map raw KMAS fields at backend boundary: prdctNm (title fallback), title -> title; pictrWritrNm -> pictureWriter; sntncWritrNm -> storyWriter; imageDownloadUrl -> thumbnailUrl; outline -> description; mainGenreCdNm -> genre; ageGradCdNm -> ageRating; pltfomCdNm -> platforms (array after merging). Preserve source mastrId when present, distinct from internal stable webtoon ID. Missing source IDs and duplicates require validation, no ISBN-only assumption. Local likeCount/isFavorite are not KMAS fields.

## Popular webtoons
GET /api/webtoons/popular accepts optional genre, platform and keyword filters. Return webtoon DTOs including likeCount (number of current favorite_webtoons rows per webtoon). Exclude zero-count works, order by count DESC then internal webtoon ID ASC for stable ties. No ranking table is needed. Apply filters before ranking; the frontend displays consecutive rank numbers within the filtered list. Home shows first four; explore shows the full returned list. For real backend, aggregate favorites before joining platform data or use distinct user IDs to avoid multiplying counts. Unlike removes the favorite and decreases the count.
